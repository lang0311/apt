# 01. 프로젝트 목적 · 서비스 정의

## 1. 한 문장 정의

> SNS(인스타그램 릴스 등)에서 발견한 장소를 **"공유" 한 번으로 앱에 가져와 자동으로 구조화·저장**하고,
> 개인 및 그룹(파티)의 취향을 반영해 **AI가 실제 방문 가능한 코스를 만들어 주는**
> 장소 저장·추천·코스 플랫폼.

앱 카피: **"가고 싶은 곳을, 하나의 코스로."**

## 2. 해결하려는 문제

- SNS에서 본 장소는 **저장해도 흩어진다** (게시물 저장함에 묻힘, 장소 정보는 캡션/영상 속에만 있음).
- 저장한 장소들을 **코스(순서·동선·시간)로 엮는 일**이 번거롭다.
- 여럿이 갈 때는 **서로 다른 취향을 맞추기** 어렵다.

## 3. 핵심 시나리오

1. **수집**: 릴스에서 `공유 → 우리 앱` → 서버가 장소를 추출 → 사용자가 확인 후 저장
2. **보관**: 카테고리(유형별) · 보관함(목적별)으로 정리, 지도에서 탐색
3. **코스 생성**: 저장한 장소를 고르면 AI가 빈 시간·동선을 채워 코스를 완성
   - 정보 → 장소 → 동행 → AI 추천 → (장소 수정 ↔ AI 재추천 반복)
4. **파티 코스**: 함께 가는 사람을 초대하면 **파티원 취향을 종합**해 추천
   - 취향 출처: ① 직접 입력한 취향(명시적) ② 각자 저장한 장소에서 추론한 취향(암묵적)
5. **트렌디한 추천**: 추천은 LLM 기반이며 **"요즘 뜨는 곳"을 반영하는 것이 핵심 가치**

### 서비스 순환 구조

```
SNS 발견 → 공유 → 추출 → 저장 → 분류 → 지도 탐색 → 코스 생성
→ 개인/그룹 추천 → 실제 사용 → 행동 데이터 → 취향 개선 → 더 나은 추천
```

이 순환이 앱 안에서 끊기지 않게 연결되는 것이 UX의 최우선 목표다.
**입력은 최소화**한다 — 공유 → 확인 → 저장이 몇 번의 탭으로 끝나야 한다.

## 4. 사용자

| 구분 | 설명 |
|------|------|
| 주 사용자 | SNS로 장소를 자주 발견하고 데이트/모임/여행을 계획하는 20–30대 |
| 코스 주최자 | 코스를 만들고 파티원을 초대하는 사람 |
| 파티원 | 초대 링크로 참여해 취향/저장 장소가 추천에 반영되는 사람 |

## 5. 책임 분담 (중요)

| 영역 | 담당 |
|------|------|
| Flutter 앱 (UI, 상태, 공유 수신, 지도 표시, API 연동) | **우리 (이 프로젝트)** |
| SNS 게시물 분석 · 장소 추출 · Place 데이터 · 카테고리 분류 | 백엔드/AI 서비스 |
| LLM 장소 추천 · 트렌드 반영 · 그룹 취향 집계 · 추천 이유 생성 | 백엔드/AI 서비스 |
| 경로/이동시간 계산 (제공 방식 확인 필요) | 백엔드 또는 지도 API |
| DB 설계 · 인증 서버 · 푸시 | 백엔드 |

앱은 **"입력을 정확히 전달하고, 결과를 정확히 · 설득력 있게 표시"**하는 데 집중한다.
추천 알고리즘의 내부 로직은 앱이 알 필요가 없고, **목적(트렌디 + 취향 맞춤 + 동선 고려)만 이해**하면 된다.

## 6. 제품 원칙

1. 공유로 들어오는 경로가 **주 acquisition flow**다.
2. 저장 장소가 서비스 데이터의 **핵심 자산**이다.
3. 추천에는 항상 **이유**가 따라온다 (점수만 노출하지 않는다).
4. 개인정보/취향 공개 범위는 **명시적으로 안내**한다 (파티 참여 시 공개되는 정보 고지).
5. 서버 데이터는 UI에 **하드코딩하지 않는다**.
6. 화면이 복잡해지면 **단계를 나눈다** (코스 생성은 4단계 위저드).

## 7. MVP 범위

**포함**: 소셜 로그인 · 공유 수신 및 링크 입력 추출 · 장소 저장(카테고리/보관함) · 저장 지도 · 장소 상세 · 코스 생성(위저드, AI 추천/재추천) · 코스 상세/관리 · 파티 초대/참여 · 취향 설정 · 마이

**후순위**: 이메일 로그인(틀만) · 실시간 공동 편집 · 푸시 알림 · 친구 시스템 · 공개 코스/피드 · 방문 인증 · 리뷰 · 코스 복제
