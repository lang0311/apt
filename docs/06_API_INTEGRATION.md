# 06. 백엔드 연동 가이드

> 백엔드/AI는 **제공받는다.** 이 문서는 "앱이 서버에 무엇을 필요로 하는가"를 정리해 **API 명세를 받을 때/요청할 때 체크리스트**로 쓰기 위한 것이다.
> 엔드포인트, 필드명, enum은 **여기서 정하지 않는다.** (아래 예시 표기는 설명용)

> **백엔드 기준 (07 D12, 2026-10-25):** 팀 레포에 **실제로 구현된 서버 API**(GitHub 최신 `origin/main`의 `api.py`·`src/`, 로컬 clone은 `apt` 옆 `team/`)가 기준이다. API 작업 전 `git fetch`로 새 커밋을 확인하고 바뀐 API는 보고한다.
> `docs/API/API 정리.xlsx`는 서버와 작성자가 다른 초안(응답 형식 없음)이라 **서버에 없는 기능의 방향 참고로만** 쓴다. 둘이 다르면 서버를 따른다.

## 1. 연동 원칙

1. **실제 구현된 서버 코드가 Source of Truth**(그다음 엑셀 명세는 참고). 없는 필드/상태값을 추측해 구현하지 않는다.
2. 명세가 없는 기능은 `Repository Interface` + `Mock Repository`로 분리하고 `NEEDS BACKEND`로 기록한다. Widget 안에 mock JSON 금지.
3. `DTO → mapper → Domain Model → UI`. 서버 응답 구조가 바뀌어도 mapper만 수정하면 되게 한다.
4. 서버 데이터(카테고리, 취향 키워드, 보관함, 코스, 통계)는 **UI에 하드코딩하지 않는다.**
5. 서버 명세와 docs가 충돌하면 임의 선택 없이 **충돌 지점을 명시하고 제안**한다.
6. 외부 API 키(소셜, 네이버 지도, 길찾기 등)는 **앱에 비밀키를 넣지 않는다.** 클라이언트용 키만 사용하고 비밀 호출은 서버 경유.

## 2. 앱 기능별 "서버에서 필요한 것"

(필드명이 아니라 **기능/데이터** 단위)

| 영역 | 필요한 것 | 비고 |
|------|-----------|------|
| 인증 | 소셜 토큰 교환(카카오/Google/Apple), 신규/기존 판별, 계정 충돌 응답, 토큰 갱신/로그아웃, (이메일 로그인은 추후) | 에러 코드 구분(취소/충돌/기타) |
| 약관·프로필 | 약관 버전/동의 저장, 닉네임 규칙/중복, 프로필 이미지 업로드 | |
| 통계·홈 | 저장 장소 수·진행 코스 수·최근 추출 수 **aggregate**, 최근 추출 N개(홈은 최대 10, 출처 계정 이름 있으면 좋음), 트렌딩 장소, 진행 중 코스(오늘 이후 날짜, 가까운 순), 추천 코스, (선택) 어느 시각 이후 저장 수 | 전체 목록 count 금지 |
| 추출 | URL 제출 → 분석(동기/비동기), 진행 상태 조회, 결과 후보(장소·사진·키워드·원본 링크·**이미 저장 여부**), 실패 사유 코드 | 상태 enum은 명세 기준 |
| 저장 | 장소 저장/해제, 보관함 CRUD, 장소↔보관함 **다대다**, 카테고리 목록(+개수), 목록 페이지네이션, 검색/정렬 | |
| 지도 조회 | 초안: `GET /api/v1/places/nearby?lat&lng&radius(m)`. 앱은 보이는 영역을 덮는 원(중심→모서리)으로 호출하고 화면 밖은 제외. 필터·거리는 앱 처리(07 A11·A12). 응답 형식·반경 상한·bbox 지원 여부 확인 필요 | `SavedRepository.fetchSavedPlacesNearby` |

| 코스 | 코스 CRUD, 장소 순서, 일정(시각), 개인/파티 구분, 소유자/멤버 권한, 목록 summary | N+1 방지용 summary |
| 파티 | 초대 링크 생성, 초대 수락/거절, 만료·중복·인원 초과 에러, 멤버 목록, 파티원 취향 요약 | 공개 범위 정책 |
| **AI 추천** | 추천 요청(코스 상태·동행·분위기 입력), 추천 장소 + **추천 이유**, **재추천**(현재 코스 기준·이번 코스 제외 목록), **추천하지 않는 장소(차단) 목록** 저장·조회·해제, 응답 지연 처리 방식 | 아래 §3 |

## 3. AI 추천 루프를 위해 서버에 확인할 것

코스 만들기 4/4의 `수정 → 재추천` 반복을 지원하려면:

1. **입력**: 코스 이름·날짜·시작 시간·분위기·고정 장소(사용자 선택)·동행(혼자/파티ID)을 한 번에 보낼 수 있는가?
2. **재추천 의미**: "다른 추천"은 (a) 현재 코스를 유지한 채 AI 장소만 교체하는가, (b) 전체 재생성인가?
3. **제외 목록**: 두 종류를 보낼 수 있는가? (07 D24)
   - 이번 코스에서만 뺀 장소(`CourseDraft.rejectedPlaceIds`) — 이 코스를 다시 추천할 때만 제외
   - 사용자 차단 목록(`CourseRepository.fetchBlockedPlaces/blockPlace/unblockPlace`) — 모든 추천에서 제외. 서버가 계정 기준으로 빼는지, 앱이 매번 보내야 하는지
   - 저장된 코스를 다시 추천할 때(코스 편집)도 같은 API인가, 코스 ID 기준 API가 따로 있는가
4. **세션/상태**: 추천 결과가 서버에 `recommendationId` 등으로 보존되는가, 아니면 요청마다 무상태인가?
5. **응답 방식**: 동기 응답 vs 비동기(작업 ID + 폴링/스트리밍). LLM 지연 시 타임아웃 기준.
6. **응답 내용**: 장소별 추천 이유 문장, 이동 시간/도중 빈 시간 활용 설명. (취향 반영 비율은 받을 수 없다고 보고 앱에서 뺐다 — 07 D25)
7. **한도**: 재추천 횟수/쿼터 제한이 있는가, 있으면 어떤 에러로 오는가?
8. **트렌디함**: "지금 뜨는 장소"(홈), 추천 이유의 "요즘 인기" 라벨을 어떤 필드로 받는가?

## 4. 파티·취향 관련 확인

- 파티원 취향 종합은 서버가 수행하는가? 앱은 결과(요약 키워드·비율)만 받는가?
- 초대 수락 시 "내 저장 장소와 취향을 추천에 반영" 체크 값이 서버에 저장되는가? 철회 가능한가?
- 파티원에게 공개되는 정보 범위(취향 키워드, 선택 장소만)가 서버 정책과 일치하는가?
- 취향 자동 분석(저장 장소 기반)은 서버가 계산하고 앱은 on/off와 결과 키워드만 다루는가?
- 파티 코스 편집 권한(소유자만? 모두?)과 동시 수정 충돌 처리.

## 5. 공통 응답 처리

| 항목 | 앱 처리 |
|------|---------|
| 인증 만료(401) | 토큰 갱신 시도 → 실패 시 로그인으로 이동, 보류 중 공유 URL/초대 토큰 보존 |
| 권한/없음(403/404) | 도메인별 안내 화면 또는 토스트 (초대 만료 등) |
| 서버 오류(5xx)/네트워크 | 재시도 가능한 ErrorState, 스낵바 |
| 검증 오류(400/422) | 필드 인라인 오류 매핑 (닉네임, 보관함 이름, 이메일 형식 등) |
| 타임아웃 | 추출/추천은 긴 타임아웃 + 취소·재시도 UX |
| 페이지네이션 | cursor 제공 시 cursor, 아니면 page/size (명세 기준) |

## 6. Mock 전략

```
FeatureRepository (interface)
 ├── ApiFeatureRepository   ← 명세 수령 후
 └── MockFeatureRepository  ← 개발 초기, 프리뷰 화면과 동일한 샘플 데이터
```
- Mock 데이터는 `test/fixtures` 또는 `lib/dev/mock/`에 모으고 프리뷰 SVG의 문구(성수동 데이트 등)를 재사용해 시안 대비 확인을 쉽게 한다.
- `환경 플래그`로 Mock/실서버 전환 (예: `--dart-define=USE_MOCK=true`).
- Mock이 반드시 지켜야 할 것: **로딩 지연, 빈 응답, 오류 응답**을 흉내낼 수 있어야 한다 (상태 UI 검증용).
